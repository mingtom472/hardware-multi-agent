# Engineering AI Studio
## 多模型协作嵌入式硬件与电源工程智能体——开发需求书 V2.1

### 一、开发目标

你现在担任资深 AI Agent 架构师、Python 全栈工程师、嵌入式硬件工程师及电源研发工程师。

请协助我从零开发一套能够在 **Windows 本地运行** 的多模型 AI 工程智能体。

本项目不是普通聊天助手，也不是简单将多个 AI API 串联起来，而是一个能够：

- 自主理解用户需求
- 自主划分工程任务阶段
- 根据任务自动选择合适的大模型
- 让不同模型串行或并行协作
- 调用专业工程计算、仿真与分析工具
- 对模型结论进行交叉检查
- 生成准确的工程图表与分析报告
- 持续积累经过人工审核的工程案例
- 严格控制 Token 消耗及 API 费用

的专业电子工程智能体系统。

**初期核心领域：**

1. 嵌入式硬件设计与分析
2. 开关电源及电力电子设计与故障诊断

嵌入式软件工程师 Agent 初期仅预留接口和扩展能力，不作为首版必须完成的功能。系统自身的软件开发与自动化测试仍必须实现。

项目采用模块化设计，未来可以继续扩展至嵌入式软件、PCB、EMC、热设计和其他电子工程领域。

### 二、初期模型供应商及任务分配

必须优先按下表设计模型接入和任务路由。

| 工程工作 | 初期首选模型 / 技术 | 供应商 |
|---|---|---|
| 电路原理图识别 | Qwen3.8-Max | 阿里云通义千问 |
| 电源拓扑及故障推理 | GPT-6 Astra | OpenAI |
| C/C++、MCU 软件开发 | Claude Opus 5.5 | Anthropic |
| 大量芯片手册分析 | Kimi K3.1 Pro | 月之暗面 |
| 工程计算与独立复核 | GPT-6.1 Sol | OpenAI |
| 自动编译、调试、执行 | Claude Agent / Agent SDK | Anthropic |
| 低成本批量检查 | DeepSeek V4.1 Flash | DeepSeek |
| 技术讲解配图、图片生成及编辑 | GPT-Image 系列 | OpenAI |

**重要：上述分工是初期默认路由，不代表这些模型已在本项目评测中证明最优。后续必须允许根据实际工程评测结果修改。**

#### 2.1 API 接入要求

初期完成五家供应商的适配层：

- Alibaba Cloud Model Studio
- OpenAI
- Anthropic
- Moonshot AI
- DeepSeek

优先配置的模型标识包括：

- `qwen3.8-max`
- `gpt-6-astra`
- `gpt-6.1-sol`
- `claude-opus-5-5`
- `kimi-k3.1-pro`
- `deepseek-flash`
- GPT Image 当前支持的具体模型 ID

以上为目标模型配置名称，开发时必须核对供应商真实 API model ID、访问权限及可用性，不得把尚未验证的名称视为一定可调用。

Claude Agent 使用独立的 Agent SDK 或相应运行时适配器，不作为普通文本模型 ID 接入。

所有模型 ID、供应商 URL、API Key、调用参数均应可配置。实际调用之前必须检查账号权限、接口兼容性和模型能力，不能假定所有 API 功能完全一致。

#### 2.2 模型调度规则

支持三种策略：

**A. 自动智能调度**

总控智能体分析任务内容、复杂度、所需工具和预算，自主选择合适的模型。

**B. 手动模型调度**

用户可以指定哪个模型负责识图、分析、审核、计算和最终输出。

**C. 混合调度**

用户锁定部分模型，其余阶段由总控智能体自动决定。

一个模型允许承担多个任务；一个任务也允许调用多个模型独立分析。

不能强制所有任务经过全部八个环节。

### 三、总控智能体 Orchestrator

这是整个系统的核心。

总控智能体负责：

1. 理解用户的真实目标。
2. 识别上传文件及其用途。
3. 将目标拆分为可执行的阶段。
4. 判断每个阶段需要的模型和工具。
5. 自动建立任务依赖关系。
6. 在适当情况下并行执行不同阶段。
7. 保存每个阶段的结果。
8. 处理模型输出不一致的问题。
9. 检查是否达到用户要求。
10. 生成最终成果并交付。

建议使用 LangGraph 实现动态工作流与状态管理。

需要支持以下执行模式：

- 串行执行
- 并行执行
- 条件分支
- 阶段重试
- 人工审核
- 失败恢复
- 中途取消
- 任务历史恢复

总控模型本身也必须可配置。

禁止在没有终止条件的情况下让多个模型无限讨论。

每个任务应具有清晰的完成条件、最大执行轮次和成本上限。

### 四、嵌入式硬件工程师 Agent

这是第一阶段重点建设的专业 Agent 之一。

#### 4.1 核心能力

要求逐步支持：

- 电子电路基础分析
- 原理图识别与元件连接分析
- 模拟电路与数字电路分析
- MCU 最小系统分析
- 时钟、复位、供电电路分析
- ADC/DAC 接口分析
- MOSFET、BJT、运放、比较器电路分析
- UART、SPI、I²C、CAN、RS485 等接口电路
- Datasheet 阅读及关键参数提取
- 器件选型、BOM 和参数裕量检查
- 电气连接错误检查
- 上电异常及硬件故障定位

#### 4.2 原理图识别流程

用户上传原理图图片后：

1. 优先由 Qwen3.8-Max 识别器件、型号、参数和连线。
2. 输出结构化识别数据。
3. 标注无法识别或存在歧义的区域。
4. 将原图和识别结果交给专业分析 Agent。
5. 对关键器件连接和参数进行独立检查。
6. 生成电路功能分析与风险报告。

必须允许模型指出图片分辨率不足或识别结果不确定。

不得在缺少依据时擅自补全不存在的连接。

如果用户上传可编辑的 KiCad 原理图或网表，优先通过工程文件解析真实连接，并结合 ERC 等工具检查。

### 五、电源与电力电子工程师 Agent

这是首版最重要的专业功能模块。

#### 5.1 专业范围

初期优先实现：

- Buck
- Boost
- Buck-Boost
- 同步 Buck
- Flyback

后续扩展：

- Forward
- LLC
- CLLC
- DAB
- GaN / SiC 电源设计
- 其他高频高功率密度拓扑

#### 5.2 工程计算

应能够完成：

- 占空比计算
- 电感设计与纹波计算
- 电感峰值电流与 RMS 电流
- 输出电容及 ESR 纹波
- MOSFET 导通损耗
- MOSFET 开关损耗
- 电感与电容应力分析
- 器件额定值裕量检查
- 功率损耗与效率估算
- 负载瞬态计算
- 电源控制与环路基础分析

计算优先采用经过单元测试的 Python 函数。

模型负责选择正确的分析方法、判断公式适用范围及解释计算结果。

所有公式必须：

1. 定义每个符号。
2. 明确单位。
3. 说明适用条件。
4. 给出计算过程。
5. 列出关键工程假设。
6. 明确误差来源与结论限制。

#### 5.3 故障诊断

逐步建立以下分析能力：

- 电源输出电压异常
- 电源启动异常
- SW 节点振铃
- 电感饱和
- MOSFET 过热
- CS 检测尖峰
- 逐周期限流异常
- 死区时间异常
- 体二极管反向恢复
- 负载瞬态异常
- 环路稳定性问题

默认由 GPT-6 Astra 承担复杂电源故障推理，由 GPT-6.1 Sol 承担重要计算与独立复核。

必要时调用其他模型交叉审查。

严禁无证据地给出确定性故障根因。

系统必须区分：

- 已证实的事实
- 工程理论推导
- 仿真结果
- 实际测量结果
- 尚未验证的假设

### 六、专业工程工具

必须优先建立真正的工具调用能力。

首批工具包括：

- Python
- NumPy
- SciPy
- Pandas
- Matplotlib
- ngspice
- PDF 文本与表格解析
- 示波器 CSV 分析工具

应优先实现：

**示波器波形分析**

支持上传 CSV，提取 VOUT、IL、SW、FB、CS 等数据，并根据实际通道和采样信息完成计算。

能够输出：

- 实际波形曲线
- 峰峰值
- 最大值与最小值
- 电压跌落量
- 过冲量
- 电流上升斜率
- 恢复时间
- 数据及采样条件说明

不得通过图片生成模型伪造测量波形。

**电路仿真**

允许生成并执行 ngspice 可识别的仿真网表。

必须能区分仿真成功、仿真失败以及结果尚未验证。

**自动化执行**

预留 Claude Agent SDK 接口，供后续实现文件操作、代码生成、编译和调试。

首版不要求实现完整 MCU 固件自动开发系统。

涉及运行不可信代码、修改关键文件或操作真实硬件时，必须有权限控制与人工确认。

### 七、芯片资料智能分析

初期指定 Kimi K3.1 Pro 为长文档分析首选模型。

用户上传 Datasheet、Reference Manual、Application Note 等资料后，系统应支持：

- PDF 文本、表格及关键图片提取
- 器件型号识别
- 核心参数提取
- 参数适用条件识别
- 绝对最大额定值检查
- 推荐工作条件分析
- 典型应用电路分析
- 器件间参数比较
- 可追溯的文档引用

必须建立 RAG 检索机制。

不要每次分析时将整份大型文档发送给全部模型。

保留文档厂商、型号、版本、页码及引用依据。

模型无法确认的参数必须明确标注，不得编造。

### 八、多模型独立复核

对于重要工程结论，必须支持独立审核。

例如：

用户上传同步 Buck 电路及负载瞬态波形，要求分析 VOUT 跌落及 IL 上升异常。

推荐执行流程：

1. Qwen3.8-Max 识别原理图和关键参数。
2. GPT-6 Astra 建立故障分析假设。
3. GPT-6.1 Sol 独立进行计算复核。
4. Python 从真实 CSV 中计算波形指标。
5. 当分析存在分歧时，调度 Claude Opus 5.5 或其他合适模型进行独立审核。
6. 汇总证据、分析结果及未解决的问题。
7. 输出工程报告。

对不同模型的矛盾结论，不能简单采用多数投票。

必须优先根据物理规律、实测数据、仿真结果和可靠技术资料判断。

如果证据不足，要求主动给出需要补充的测试项目。

### 十一、Token 消耗与费用管理

这属于核心功能，必须在初期实现。

智能体提供：

**快速模式**

优先使用 DeepSeek V4.1 Flash 等低成本模型，必要时调用本地计算工具。

**专业模式**

根据任务选择一至三个主要模型，配合工程工具完成分析和必要审核。

**专家模式**

允许 GPT-6 Astra、Claude Opus 5.5 等模型进行复杂分析和交叉验证。

具体路由必须允许用户修改，不以模型价格作为唯一评价依据。

要求实现：

- 各模型输入 Token 统计
- 输出 Token 统计
- 缓存命中统计（供应商支持时）
- 单次调用费用
- 单任务累计费用
- 每日及每月费用
- 用户设定的预算上限
- 任务最大调用次数
- 最大重试次数
- 超预算停止新调用
- 费用报告导出

设置预算预检、预留费用和实际费用对账机制，不能仅靠已经发生的账单来判断是否超支。

Token 数量和费用应区分供应商真实返回值与本地估算值。

禁止为了提高表面分析质量而进行无意义的多模型循环。

### 十三、文件上传与管理系统

**核心要求：用户上传的文件类型和文件大小不设置人为的固定限制。**

该要求必须作为系统设计原则，而不是仅仅去掉前端上传组件的大小校验。

#### 13.1 文件类型

原则上允许用户上传任意文件类型，包括但不限于：

- 图片：PNG、JPG、WEBP、BMP、TIFF、SVG 等
- 文档：PDF、DOCX、TXT、MD 等
- 表格：CSV、XLSX、XLS 等
- 程序：C、CPP、H、PY、JSON、XML 等
- 电子工程文件：KiCad、Altium 导出文件、网表、SPICE、Gerber 等
- 测试数据：CSV、DAT、BIN、LOG、示波器原始数据等
- 压缩包：ZIP、7Z、RAR 等
- 其他用户自定义格式

对于尚无解析器的文件，应允许保存原始文件，并提示当前是否支持内容解析。

**允许上传不等于允许执行。任何可执行文件或不可信脚本都不能因上传成功而自动获得执行权限。**

#### 13.2 文件大小

不设置固定的 10MB、100MB、1GB 等产品层面单文件上传上限。

系统应根据用户电脑的实际存储能力和运行环境，尽可能支持大型工程文件。

必须考虑：

1. 流式上传
2. 分块上传
3. 断点续传
4. 大文件分块读取
5. 异步解析
6. 增量数据处理
7. 上传进度显示
8. 上传中断恢复
9. 存储空间监控
10. 文件完整性校验
11. 临时文件清理
12. 资源占用管理

不允许因为文件较大就直接将整个文件加载到内存中，导致程序崩溃。

遇到硬盘空间不足、文件系统限制或 API 上传限制时，必须给出真实原因和可操作的处理方案。

#### 13.3 大文件与大模型协作

不得将“文件上传成功”等同于“模型能够一次性读取整个文件”。

对于超出模型上下文窗口或 API 单次上传限制的内容，应该采用：

- 文件分块
- 局部提取
- 语义检索
- 流式分析
- 分阶段分析
- 中间结果缓存
- RAG 检索
- 大数据本地计算

例如，用户上传数 GB 的示波器数据时，优先通过本地程序处理原始数据，只将相关指标、必要的波形片段和分析证据传递给大模型。

#### 13.4 安全与可靠性

文件类型和大小不设人为固定限制，但必须保留：

- 文件路径安全检查
- 文件完整性校验
- 压缩包解压安全保护
- 恶意文件隔离
- 资源消耗监控
- 超时与取消机制
- 用户文件访问权限控制

不得自动执行上传的程序，不得允许压缩包路径穿越或解压炸弹导致系统资源耗尽。

### 十四、软件界面

开发面向 Windows 用户的中文工程工作台。

推荐初期使用 Streamlit，后续可升级到 React。

核心界面包括：

1. **AI 工程工作台**：输入需求、上传任意类型文件、选择任务模式。
2. **模型管理**：配置五家供应商 API、模型 ID、密钥和连接测试。
3. **智能体执行监控**：展示阶段、模型、进度、中间结果和错误。
4. **工程分析页面**：展示电路分析、公式、波形、测试数据。
5. **资料知识库**：导入及检索工程文档。
6. **成本控制台**：展示 Token、费用、预算和调用历史。
7. **任务历史与纠错**：查看历史结果，提交人工修改与审核。
8. **文件管理中心**：显示上传进度、文件大小、解析状态、存储位置和处理结果。

支持 Markdown、CSV、PNG、PDF 等结果导出；其他格式根据实际功能逐步扩展。

界面应简洁、现代，重点是工程效率和可靠性，不要过度追求视觉装饰。
